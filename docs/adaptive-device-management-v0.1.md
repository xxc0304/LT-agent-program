# 设备自管理与最小场景适配 MVP

## 本次实现

1. **扫描时监测能力变化**：家庭清单每次成功扫描都会比较实体的动作支持状态；发现支持/不支持/未知之间发生变化时，返回 `capability_changes`，并在该设备记录 `last_capability_change`。同一进程连续扫描还会报告 `availability_changes`。在线状态仅作为运行期观察，不写入长期清单。
2. **基于已登记设备生成房间最小节能方案**：新增 OpenClaw 工具 `plan_room_energy_saving`，从 HA 最新扫描结果中选出指定且经用户确认的房间里，已经批准、明确授权节能、在线、状态为 `on` 且 HA 明确报告支持 `turn_off` 的灯和开关/插座。
3. **设备不齐时做安全的部分规划**：只要存在可执行子集，就给出该子集的计划，并逐项列出已关闭设备和跳过设备的原因（例如离线、未授权、动作不支持、能力未知、空调/窗帘不属于此最小场景）。它不为了“凑完整场景”自动发明等效动作。
4. **确认与执行前重新校验**：多设备计划必须先展示并获得用户后续明确同意。执行前再次扫描；设备、状态、能力、授权变化会导致旧计划失效。执行期间每个设备返回独立结果和状态回读；部分失败时停止后续动作，不自动盲目重试。
5. **HA/Mock 只读状态事件监测、周期巡检、离线防抖告警与诊断**：新增 `start_household_device_monitor`、`stop_household_device_monitor` 和 `get_household_device_monitor_status`。用户明确要求后，真实 HA 模式通过 WebSocket 订阅 `state_changed`；Mock 模式接收模拟设备状态事件。`off` 是正常状态；`unavailable` / `unknown` 先进入离线待复查，默认普通实体等待 2 分钟，显式配置的安全关键实体等待 15 秒，之后重新扫描 HA 并诊断；仍离线才产生告警。宽限期内恢复时只写脱敏 `diagnostic_transient`，不生成故障告警。清单或诊断不可用时保留待复查并重试，不误报恢复或离线。3 台及以上同时持续离线时，普通设备告警合并为一条 `diagnostic_shared_infrastructure_suspected`，避免把可能的断电/网络/HA 故障拆成多台设备故障；**只有宽限期复查确认仍离线的设备才计入聚合门槛。若三个或更多设备正处于离线核查，普通设备的单台告警会暂缓，待其他核查完成后再确定是共同问题提示还是单设备跟踪；这可避免同一批掉线既报多条设备故障又报共同风险。**明确配置的安全关键实体仍单独告警。确认离线数量降到阈值以下后写 `diagnostic_shared_infrastructure_cleared`，剩余普通设备恢复单独跟踪。系统不自动断言根因。相同故障状态不会重复新增告警；正式单设备告警后恢复健康产生 `diagnostic_recovered`，实体从成功清单中消失产生 `diagnostic_tracking_ended`。不会控制或自动修复设备，也不保存原始状态/属性或令牌。真实 HA 连接断开会有限速重连，认证失败停止重连；监测仅在当前 OpenClaw 插件进程内有效。
6. **房间场景缺口分析与显式反馈适配**：`analyze_room_energy_adaptation` 按最新设备清单、用户确认房间、登记审批、节能授权、在线状态和动作能力输出 `ready/partial/blocked`、覆盖概况和下一步完善建议。`record_room_energy_scenario_feedback` 仅在用户明确反馈后，记录“有帮助/效果不佳”，或为一台已发现且房间已确认的设备设置优先、排除、恢复默认。优先设备只有通过所有既有安全条件后才会在计划中优先展示；排除设备会从之后该房间的计划中移除。`get_room_energy_adaptation_report` 跨重启保留设备偏好、反馈计数及执行回读统计。

## 当前边界

- 最小场景目前仅处理已授权的灯和开关/插座 `turn_off`。空调、窗帘、传感器、门锁不会被自动替代；要拓展须先明确设备角色、等效关系和安全条件。
- 扫描差异检测仍是按工具调用触发；新增 WebSocket 监测是显式启停的进程内只读订阅，不是独立常驻后台服务，也不是故障自动修复或自动控制。
- Mock 模式监测的事件只来自模拟设备操作或专用离线演示，不代表真实传感器。真实 HA 模式若运行环境没有可用 WebSocket，会报告不可用。进程退出/重启后监测停止，不会自动恢复。
- 房间、设备身份和节能授权都仍需用户明确确认；系统不会从设备 ID 或自然语言猜测。
- 当前个性化是**用户明确反馈驱动的设备范围适配**，不是大模型自行观察或推断习惯。系统不会自动发明任意设备动作、场景触发器或新增控制权限；偏好不能代替设备审批、房间确认、节能授权与能力证据。
- 当前效果评估只统计动作尝试和 HA 状态回读验证率，不能据此宣称节能率；尚无实测 kWh/功率基线、自动对照实验、用户画像模型或自动场景触发器。
- 真实 HA/真实设备尚未联调；自动化测试使用 Fake WebSocket，演示使用合成/Mock 数据，不可表述为实机监测或控制结果。
- 本次 Mock 闭环演示会模拟一次状态推送漏报，由周期巡检发现离线并触发诊断，再模拟外部恢复以验证清除活动告警和记录恢复事件；恢复不是系统自动修复。仍没有故障自动修复或跨进程后台服务。

## 离线验证

在 `device-manager` 目录运行：

```powershell
npm test
npm run demo:adaptive-energy
npm run demo:device-monitor
```

设备监测演示应显示：短暂离线只记瞬时事件；单台持续离线经过宽限期后产生设备告警；三台同时持续离线时普通设备告警合并为一条共同基础设施提示；降到阈值以下后剩余设备恢复单独跟踪。全程不控制或修复设备，也不会访问真实 HA/家电。节能计划演示另由 `npm run demo:adaptive-energy` 覆盖。

节能场景逐步完善流程：先通过 `discover_household_devices` 发现设备并人工核对/授权，再用 `analyze_room_energy_adaptation` 查看场景缺口；通过 `plan_room_energy_saving` 预览、确认并执行；用户明确反馈设备偏好或效果后，调用 `record_room_energy_scenario_feedback`，后续计划会应用已保存的该房间偏好。`get_room_energy_adaptation_report` 可查看反馈计数和动作回读统计。档案默认位于 `$OPENCLAW_STATE_DIR/device-manager/scenario-adaptation.json`（未设置时为用户主目录下 `.openclaw/device-manager/scenario-adaptation.json`），也可由 `DEVICE_MANAGER_SCENARIO_PROFILE_PATH` 指定。只存结构化偏好/计数，不存聊天原文。Mock 测试不证明真实家庭中实际节电。

## 后续迭代

1. 有真实 HA 后对照不同集成返回的能力字段，验证 Registry 和动作证据。
2. 选择一个真实房间、少量安全设备，完成发现—核对—授权—计划—确认—执行—回读闭环。
3. 与项目组确认“等效能力”映射（例如只关灯和切断插座是否都算满足某个场景）；对插座控制必须确认其负载用途。
4. 接入可读取的能耗计量设备并建立基线/对照周期，才可从动作回读进入实际节能效果评估；新增场景触发器须另行定义可信事件源、触发条件、冲突处理和撤销流程。
