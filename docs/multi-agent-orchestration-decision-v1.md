## A/B/C 首轮结果能说明什么

首轮每种方法各跑了 8 个合成场景、每场景 1 次。复核 24 个原始文件后，三种方法在 S01–S08 使用的用户输入文本逐条相同，模型记录均为 DeepSeek `deepseek-v4-flash`。原始文件标注 A/B 为 `r2`、C 为 `r1`；汇总表中的总 token 与专家 token 列缺失，且没有重复样本。因此只把它作为路由行为的探索性观察，不用它给方案排名。

| 方法 | 首轮可复核的行为 | 暂时不能推出的结论 |
|---|---|---|
| A 老师的 `AGENTS.md` 路由 | 8 个场景中有 7 个通过 `sessions_send` 联系专家；S05 由主 Agent 直接处理。S06 的低可信占用事件和 S08 的越界维修请求仍被发给设备专家。 | 不能说明规则外任务都会被正确识别，也不能说明 7 次派发都必要。 |
| B 项目编排器 | 8 个场景都调用编排入口；工具随后返回完成、澄清、冲突、确认、阻断或不支持等不同状态。S03 出现了“需澄清”后又完成的两次编排调用。 | 调用统一入口不等于必须派发专家；一次样本不足以判断澄清是否多余，也无法据此比较总开销。 |
| C 经理式 Agent-as-tools | 主 Agent 直接调用专家工具；S03 组合设备与能源专家，S04–S06 出现设备与安全专家的组合，S08 仍先调用设备专家。 | 不能说明专家调用次数在其他家庭规模、其他提示或重复运行中会相同。 |

从每个主会话记录重算的 token 只覆盖主 Agent：A 45,522、B 61,050、C 53,927；专家调用的完整 token 没有在同一汇总口径中，因此这不是方案总 token，也不能用来比较费用。旧报告里的 50,070 / 66,930 / 82,120 不能作为最终排名。

这些观察支持一个待验证的问题：B 的程序化校验有可追踪状态，但每条消息都要先走一次编排工具；A/C 的直接委派更灵活，也更容易出现多余专家调用或漏掉统一校验。按需调用的 D 候选值得实验，但尚未证明它能同时保持质量、安全和低开销。

## 待验证架构候选

```text
用户指令 / 家庭事件
        ↓
OpenClaw 主 Agent：理解意图，决定直接回答、澄清、拒绝或提交精简计划
        ↓
orchestrate_household_agents：唯一的家庭 Agent 派发入口
        ↓
平台编排器：校验登记能力、输入、依赖、互斥动作、权限和停止条件
        ↓
适配器：按步骤调用一个或多个获准的 OpenClaw Agent
        ↓
业务 Agent：分析、形成建议或按已有设备策略提出动作
        ↓
平台编排器：检查结构化回执，停止后续步骤或汇总结果
        ↓
OpenClaw 主 Agent：向用户解释结果；需要信息时自然语言追问
```

OpenClaw 主 Agent 是面向用户的意图理解和计划提出者。平台编排器是代码实现的校验与派发层，不是另一个大模型。专业 Agent 负责各自领域的分析和设备策略；设备管家继续通过现有设备适配器访问 HA，并负责设备清单、执行授权、确认与状态回读。编排器本身不直接操作 HA。

### 按任务选择最小必要路径（候选策略）

这是一个统一编排架构里的两种计划粒度：简单请求采用老师 A 方案启发的单 Agent 快速路由，直接明确目标 Agent 与能力；复杂请求由主 Agent 提交包含依赖的多步骤计划。两种粒度都提交给 `orchestrate_household_agents`，使用同一能力登记、策略校验和 OpenClaw 适配器。因此保留了 A 方案少调用的特点，也让所有 Agent 调用经过同一控制入口；不会维护两套互相绕开的调度器。

| 请求类型 | 处理方式 | 约束 |
|---|---|---|
| 闲聊或与家庭状态无关的问题 | OpenClaw 主 Agent 直接回复 | 不调用业务 Agent。 |
| 意图明确、单一能力、只读查询 | OpenClaw 提交一个步骤的精简计划，按老师 A 的领域说明选择单一 Agent | 仍经过统一登记表与适配器；不要求无关 Agent 做安全审查或重复查询。 |
| 明确的跨领域请求 | 提交包含必要步骤和依赖的计划 | 能并行的独立只读分析并行运行；依赖结果按顺序传递。 |
| 需要改变设备状态 | 把完整设备意图交给一个设备管家步骤 | 设备管家重新读取当前设备与状态，执行自己的家庭策略和确认要求；编排器不代替设备授权。 |
| 意图含糊、输入互相矛盾或信息不全 | 返回 `NEEDS_CLARIFICATION`，不派发受影响步骤 | OpenClaw 用日常语言询问用户；用户回答后生成新计划。 |
| 目标明确但没有对应能力，或步骤越权 | 返回 `UNSUPPORTED` / `BLOCKED` | 说明当前能力边界，不伪造 Agent、结果或执行成功。 |
| Agent 失败、超时或设备结果不确定 | 停止未开始步骤并回传明确状态 | 可能已产生副作用的请求不自动重发；设备管家负责按设备流程查询实际状态。 |

对于需要确认的门锁或其他敏感操作，聊天中的“好”不能替代独立身份认证或设备授权。模型和提示词都不能自行解除工具层或设备管家的安全门禁。

## 如何使用老师的 `AGENTS.md`

老师的文件是实验 A 的路由基线，也可作为 Agent 职责描述和自然语言路由示例的来源。将确认过的职责、能力边界和典型请求整理成主 Agent 可读的简洁说明，并同步到 Agent 能力登记。运行时仍由编排工具校验 Agent ID 与能力，避免提示词直接调用未登记或未授权的目标。

不得从老师文档中推导出未定义的能源、学习或其他 Agent 能力。确需新增能力时，先补 Agent 登记、适配器、输入输出契约和测试，再允许模型提出相应计划。

## 控制 token 和延迟的设计要求

1. 单步只读请求使用最精简的结构化计划；不为每个家庭请求强制生成多 Agent DAG。
2. 主 Agent 只提交任务所需的房间、设备快照、偏好和事件字段，适配器只向目标 Agent 发送该步骤所需数据。
3. 不重复调用已返回足够证据的 Agent；只有依赖或关键输入缺失时才补查，并把缺少的数据名称说明清楚。
4. 独立只读分析可以并行；有数据依赖的步骤顺序执行；设备动作步骤等待相关分析完成。
5. Agent 返回明确的 `COMPLETED`、`PROPOSED`、`NO_ACTION`、`NEEDS_CLARIFICATION`、`NEEDS_CONFIRMATION`、`CONFLICT`、`BLOCKED` 或 `FAILED` 状态。预期业务拦截不包装成运行时异常。
6. 能源数值必须携带单位、币种和时间范围；缺失时追问或标记未知，不让模型补猜。
7. 记录模型轮次、token、端到端延迟、各 Agent 调用数、澄清率、路由正确率和安全违规数。API 费用、CPU、内存和并发没有实测时标为未知，不作估算。

## 与现有实现的对应关系

本方案的核心链路已在仓库实现：

- `multi-agent-orchestrator/src/openclaw-platform-plugin.js` 注册 `orchestrate_household_agents` 主工具。
- `multi-agent-orchestrator/src/platform-agent-registry.js` 登记 Agent 及能力。
- `multi-agent-orchestrator/src/platform-orchestrator.js` 校验计划、依赖与可见冲突，派发独立步骤并在停止状态下阻止后续步骤。
- `multi-agent-orchestrator/src/openclaw-platform-adapter.js` 通过 OpenClaw 的 Agent 调用接口派发任务，并检查 A2A 白名单与会话可见性。
- 设备管家继续持有真实设备适配、确认和执行边界。

因此，本阶段主要是定稿路径选择和降低不必要调用的设计，不需要再新造一个调度框架。若实现阶段需要改变计划格式、派发权限或设备动作策略，应以本决策为基准单独修改并验证。

## 定稿前仍需验证

1. 修复 S03 设备快照在主 Agent 计划与依赖结果中的传递，验证缺失与漏传能被区分。
2. 将 `BLOCKED`、`NEEDS_CONFIRMATION` 等业务状态作为正常结构化结果回传，不产生工具异常语义。
3. 给能源输入补充必需的币种、单位和周期字段，并验证缺失时不会推测。
4. 对核心场景进行多次重复，报告各方案每个场景的成功、部分成功、误路由、澄清、安全违规、token 和延迟范围。
5. 采集隔离 Gateway 的 CPU/RSS 基线和运行峰值；如要比较并发，使用相同请求数和环境。云端模型推理资源与本地 Gateway 资源分别报告。
6. 老师的两个 Agent ID、项目 Agent 能力与实验 fixture 并非完全一致。定稿报告要明确这类覆盖映射，不把 fixture 说成已部署的正式 Agent。
7. 实时查询场景不能把 Mock 传感器值直接放进用户消息；共享状态必须由 Mock 查询能力或可信事件上下文提供，并验证回答引用的是查询后的当前状态。

此前“推荐 B 为当前研发主线”的表述撤回。当前没有最终方案，也没有证据证明某种方法在智慧家庭里普遍最优。下一步先补齐公平的 A/B/C/D 对照和家庭状态模拟验证，再根据质量、安全、必要调用率、资源和故障恢复结果决定是否采用候选链路。
