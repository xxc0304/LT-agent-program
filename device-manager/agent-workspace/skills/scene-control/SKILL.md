# 家庭场景控制

用户明确要求“回家模式”“睡眠模式”或“离家模式”时使用本 Skill。只允许调用现有场景，不要把自然语言临时拼成未定义的批量设备动作。

## 场景映射

- 回家模式 → 调用只读 `plan_scene`，`scene_id: "home"`。
- 睡眠模式 → 调用只读 `plan_scene`，`scene_id: "sleep"`。
- 离家模式 → 调用只读 `plan_scene`，`scene_id: "away"`；该场景不读取温度偏好。

如果用户意图不明确，先询问；若用户提出的组合不属于上述场景，说明当前没有对应预定义场景，不得冒充已执行。

## 按房间适配的最小节能方案

用户提出“这个房间节能”“离开书房后关掉可控灯和插座”等房间级多设备节能请求时，可以调用 `plan_room_energy_saving`，传入已由用户确认的 `area_id`。该工具会刷新 HA 设备清单，并只选择同时满足以下条件的灯/开关/插座：设备及房间已核对、设备已批准、用户明确授权节能、设备在线、当前为 `on`，且 HA 明确提供 `turn_off` 支持证据。

计划可以是部分计划：必须列出将执行的设备、已处于目标状态的设备、以及未授权/离线/能力未知/不支持或不属于当前最小场景的设备和原因。不要把“部分完成”表述为房间设备已全部覆盖；不要猜测空调、窗帘或其他设备的等效动作。插座负载用途未经确认时，不要建议用户开启对该插座的节能授权。

将完整计划展示给用户后，必须等后续独立消息的明确同意，再调用 `execute_room_energy_saving_plan`。执行前状态、能力、设备授权或计划内容变化时，旧计划会失效，应重新预览并再次确认。执行中出现失败或结果不确定时停止，不自动重试；按逐设备回读如实汇报。Mock 后端下明确说明为模拟演示。

### 场景逐步完善与个性化

- 用户问“这个房间目前能做哪些节能”“为什么有设备没参与”“场景还缺什么”时，先调用 `analyze_room_energy_adaptation`，用返回的 `ready/partial/blocked`、跳过原因和 `improvement_suggestions` 解释现状。它是只读分析，不代表所有设备都已覆盖。
- 只有用户明确评价“有帮助/效果不好”，或明确要求某台设备优先/排除/恢复默认时，才调用 `record_room_energy_scenario_feedback`，并令 `user_explicit_feedback: true`。设备偏好请求必须带清单中的 `device_id`；若房间未经确认或设备不在该确认房间，先澄清/让用户核对，不保存偏好。不得从沉默、一次性指令、传感器事件或普通对话推断长期偏好。
- 用户要求查看迄今的适配情况时，调用 `get_room_energy_adaptation_report`。只报告已保存的结构化偏好、反馈次数和动作回读统计。除非系统接入真实能耗计量和基线数据，不能报告节省了多少电或节能百分比。
- `prefer_device` 只是展示优先级，不是控制授权；`exclude_device` 会从该房间后续最小节能计划中排除设备；`reset_device_preference` 恢复默认设备筛选。任何偏好都不能绕过登记批准、房间确认、节能授权、在线状态和 HA 动作能力检查。
- 方案会随设备清单和明确偏好重新计算，但当前不会自行生成任意新场景、后台自动触发场景或自动执行。诸如“孩子离开书房后自动关灯”的触发条件，必须另行接入可信占用事件并由用户确认自动化规则；不能把一次手动方案预览说成自动化已经建立。

用户明确要求持续监测设备状态变化时，可使用 `start_household_device_monitor`；真实 HA 通过 WebSocket 订阅，Mock 使用模拟事件。事件会防抖刷新设备清单并触发只读健康诊断；监测期间还每分钟进行一次清单扫描和全设备健康巡检，以补发现漏报。`off` 是正常状态。`unavailable` / `unknown` 先按默认宽限期等待复查（普通实体 2 分钟；显式配置的安全关键实体 15 秒）；宽限期内恢复只写脱敏 `diagnostic_transient`，不会告警；清单/诊断失败继续待复查，不当作恢复或故障；复查仍离线才发 warning / critical。三台及以上同时离线只提示可能存在共同基础设施问题，不断言根因。正式告警后恢复健康才写 `diagnostic_recovered`；实体从成功清单消失时写 `diagnostic_tracking_ended`，不得称为设备恢复。监测不会控制设备或自动执行节能方案。使用 `get_household_device_monitor_status` 查看当前进程内连接、待复查清单、清单刷新、巡检和诊断摘要；用户要求停止时调用 `stop_household_device_monitor`。Mock 结果必须明确标为模拟，不是真实传感器数据。普通一次性查询、节能规划或控制请求不应启动持续监测。真实 HA 认证失败、WebSocket 不可用或正在重连时，必须如实说明连接状态。监测不会跨 OpenClaw 进程重启保留。

## 执行和验证

1. `plan_scene` 只返回建议步骤，绝不控制设备。它只读取 `confirmed` 温度和灯光亮度偏好；候选、过期或未确认记忆不能进入计划。若工具返回 `PREFERENCE_CONFLICT`，不要展示或执行场景默认值来绕过冲突；应向用户展示对应设备/房间的候选值并询问采用哪一个，待记忆冲突解决后重新规划。工具返回的 `plan_id` 仅供后续工具调用关联当前方案，不要展示给用户，也不要让用户输入。
2. 仅当空调在线、温控上下限已知且温度偏好在范围内时，才个性化温度；仅当灯具在线且 HA 已明确支持亮度调节时，才个性化亮度。否则保留场景固定值并说明原因。灯具明确不支持/未知能力时不得把推测值写入执行计划。
3. 向用户用自然语言展示完整步骤、温度/亮度、哪些值来自已确认偏好，并询问“要按这个方案执行吗？”。不要展示工具 ID、UUID 或要求用户照抄任何固定口令。
4. 只有在用户看到完整计划后、于后续独立消息中明确肯定同意（如“执行吧”“按这个方案执行”“可以，就这样”），才调用 `execute_scene_plan`，传入对应的内部 `plan_id` 与 `user_confirmed: true`。最初提出场景请求不算二次确认；否定、犹豫、反问、仅表示收到或其他含糊回复都不算同意，应先澄清。工具会检查十分钟有效期、计划是否过期/已使用，并重新读取偏好和设备条件；Gateway 重启也会使未完成计划失效。任何变化都应重新预览并再次询问。
5. 不得为了执行预览计划而直接调用 `run_scene` 或 `control_device`。`run_scene` 只保留为旧版固定参数接口；个性化场景必须通过 `execute_scene_plan` 执行，确保温度/亮度使用预览时的值并在执行后回读核验。
6. 确认后执行工具会先完整预检涉及设备，再执行并返回逐项状态验证及审计关联 ID。若预检失败，说明没有执行；若只部分成功或任一项目验证失败，逐项列出结果，不能汇报为整体成功。
7. 不要因部分失败而自动重跑整个场景，以免重复执行已成功的动作。先查询当前状态并解释结果，再由用户决定下一步。
8. 项目预定义场景不包含开锁。用户要求开锁时，转交 `device-control` 的单独确认流程。
9. 当前后端为 Mock 时，应明确标注模拟执行结果。

`user_confirmed` 是 Agent 根据后续对话作出的确认判定，不是工具可独立验证的用户身份凭据；当前流程用于避免把最初请求直接当执行授权。真实部署如需工具层可信确认，应接入 OpenClaw 原生人工审批或独立确认 UI。
